# v0.5.4 D5-A — Guided LAB implementation and verification contract

**Base:** v0.5.3.3 main `a1ef752cf7ded86436c0b071032585a27cd5322d` · **Branch:** `feat/v0.5.4-d5-guided-labs` · **PR:** #28 · **Review:** clinical expert pending.

## Implemented and user-visible flow
The existing CORE-local LAB (not a new top-level tab) has three independent activities: PEEP 5→8 cmH₂O, set f 15→18 /min, FiO₂ 40→60%. Each adds 1 prediction and 1 interpretation question, 6 total. The permitted stage sequence is **predict-unanswered → predict-answered → observation → interpret-unanswered → interpret-answered → completed**. `not-started` is the broader inactive surface; a newly opened session starts at predict-unanswered. The user may switch LABs, top-level tabs, graph types, view presets, A1 learning-only view, device visibility and viewport without erasing any submitted answer. The LAB runs even if CORE quiz was never started.

Each question uses a radio choice and explicit submit; unsubmitted options remain without feedback. Upon submit, the user's answer and all three option-specific rationales appear read-only. Submitting the same phase again or jumping ahead is rejected by pure state transitions, regardless of UI visibility. The user actively chooses to reveal observation after prediction feedback and to continue to interpretation. A final review explains model limits and source provenance. Closing/reopening keeps per-LAB sessions; an explicit per-LAB restart resets only that LAB. Page reload clears all LAB RAM by existing policy.

## No pre-answer output
The baseline/trial numeric settings and independent warning are visible from the outset. Before observation, the graph view (including legend, results and title), result note and overlap note are hidden, the SVG paths/title/desc are erased, and stale graph metadata is cleared. `#lab-result-note` and `#lab-overlap-note` original clinical/model warning strings are retained in application logic and displayed during observation. The SVG is only generated in observation and later phases.

**Constraint:** This is a static client-side education application; the correct answers exist in its `src/lab-lessons.js` source code and therefore are not secure examination secrets. The gating prevents *visible premature disclosure to a learner using the normal interface*, not forensic access through developer tools or source files.

## Model/data boundary
`src/lab-engine.js` is pure, immutable state transitions, no import of device, CORE, CASE or DOM. `src/lab-lessons.js` holds versioned questions, option-specific feedback, `objectiveIds`, source IDs, `evidenceKind`, and `review:{approved:false,status:"pending-clinical-review"}`. `auditLabLessons()` validates question count, unique IDs, two phases per LAB, distinct choice IDs/text, present answer, feedback, evidence and sources. `src/app.js` owns only per-LAB `Map` RAM sessions and the observation rendering gate. It reuses the original `compareWaveforms()` path and 0–16s/320 sample common-axis SVG.

The actual device committed settings, Pending/Accept/Cancel, fixed monitor values, waveform time/pause/inspector, CORE 10 score, CASE 4/12 score and nursing-action exercises remain unaffected. FiO₂ not changing the curves **does not** imply that a patient has no oxygenation response; this version's generator simply does not use FiO₂ as a waveform input. PEEP and f comparison are also generated examples and not PB980 firmware or patient physiological predictions.
